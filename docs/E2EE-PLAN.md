# Horizon 端到端加密（E2EE）方案与代价清单

> 状态：**方案阶段，尚未实现**。需要先确认第 6 节的 4 个问题，再决定是否动工。

## 1. 目标与威胁模型

**要防的：**
- 数据库被拖库 → 只剩密文
- 服务商（Supabase）/ 运维 → 读不到内容
- 拿到 service_role 密钥的人 → 读不到内容

**不防的（明确写清楚）：**
- 手机/电脑被入侵、App 被 root 后读内存
- 私钥文件被拷走
- 你把聊天截图发出去

换句话说：E2EE 保护“传输和存储”，不保护“已经解密的设备”。

## 2. 密钥体系

```
每个用户一对身份密钥（X25519）
  ├─ 私钥：只存在设备本地（不传服务器）
  └─ 公钥：上传到 profiles.public_key

每个会话一把对称密钥（32 字节，AES-256-GCM）
  ├─ 创建者客户端随机生成
  └─ 用每个成员的公钥分别“封装”一份，存 conversation_keys
       （每个成员一行，服务器只能看到密文包装）

消息体：AES-256-GCM(会话密钥, 明文消息)
  存储：ciphertext + nonce + sender
```

新增表/字段（草案）：

```sql
alter table public.profiles add column if not exists public_key text;

create table public.conversation_keys (
  conversation_id uuid not null references conversations(id) on delete cascade,
  user_id uuid not null references profiles(id) on delete cascade,
  wrapped_key text not null,          -- 用该用户公钥加密的会话密钥
  created_at timestamptz not null default now(),
  primary key (conversation_id, user_id)
);

alter table public.messages
  add column if not exists ciphertext text,   -- 密文（base64）
  add column if not exists nonce text,        -- 12 字节随机数
  add column if not exists e2ee boolean not null default false;
```

## 3. 关键流程

### 3.1 首次使用
1. 客户端生成 X25519 密钥对
2. 私钥存本地（Capacitor Secure Storage / IndexedDB）
3. 公钥写 `profiles.public_key`

### 3.2 建私聊 / 建群
1. 客户端生成 32 字节会话密钥
2. 拉取所有成员的 `public_key`
3. 逐个封装 → 写 `conversation_keys`
4. 会话密钥缓存到本地

### 3.3 发消息
```
明文 → AES-GCM(会话密钥) → {ciphertext, nonce} → 写 messages
```
服务器全程只看到密文。

### 3.4 收消息
1. Realtime 收到密文
2. 用本地缓存的会话密钥解密
3. 失败（没密钥/新群）→ 先拉 `conversation_keys` 解封装

### 3.5 新成员入群
由**任意已有成员**把会话密钥封装给新人（客户端完成），服务器不参与。

### 3.6 媒体（图片/语音）
上传前用会话密钥加密文件字节，Storage 里放密文；下载后本地解密再渲染。
签名 URL 即使泄露，拿到的也是密文。

## 4. 代价清单（重要）

| 能力 | E2EE 后 |
|---|---|
| 服务端全文搜索 | ❌ 失效，只能**下载后在本地搜**（大聊天会慢） |
| 推送预览文字 | ❌ 服务器读不到，只能推「你有一条新消息」 |
| 卸载 App / 换手机 | ⚠️ **私钥丢失 = 历史消息永久读不了**（除非做密钥备份） |
| 多设备同时在线 | ⚠️ 每台设备都要有一份私钥，否则只能读新消息 |
| 24 小时媒体销毁 | ✅ 不受影响（文件还是加密的，照样删） |
| 撤回 / 引用 / 称号 | ✅ 逻辑不变（引用也要加密） |
| 管理端「账号数据一览」 | ✅ 只剩元数据（邮箱/ID），看不到内容 |

## 5. 分阶段实施（我的建议）

| 版本 | 内容 | 风险 |
|---|---|---|
| **0.6** | 身份密钥对 + 公钥上报 + 会话密钥分发（不发消息，只铺基础设施） | 低 |
| **0.7** | 文字消息 E2EE（含引用、撤回、本地搜索） | 中 |
| **0.8** | 媒体 E2EE + 历史明文迁移 + 密钥备份/恢复 UX | 高 |

总计约 3 个版本，每个都要真机验证。中途任何一步出问题，用户会“发出去对方看不懂”。

## 6. 动手前必须确认的 4 件事

1. **换机/重装丢历史，接受吗？**
   - A：接受（最简单，私钥只在本机）
   - B：要提供「导出密钥」备份（多一步操作，但能恢复）
   - C：要「云备份私钥」（用你的邮箱口令加密后存服务器，安全性略降）

2. **推送只推“你有一条新消息”，接受吗？**
   想要预览就必须把摘要发给服务器 → 那就不是 E2EE 了。

3. **搜索改成“进入聊天后本地搜”，接受吗？**
   现在的“全局搜所有聊天记录”在 E2EE 下必须改成客户端逐会话下载后搜。

4. **已有的明文历史怎么处理？**
   - A：保留（旧消息明文，新消息密文；界面上不区分）
   - B：迁移（新客户端把明文加密后回写，量大、要停机）
   - C：清空（最干净，但记录没了）

## 7. 替代方案（如果想省事）

| 方案 | 效果 | 代价 |
|---|---|---|
| 不做 E2EE，只做「消息阅后即焚 / 定时清空」 | 降低暴露面 | 不防服务商 |
| 只对“敏感会话”开启 E2EE | 折中 | 实现复杂度几乎一样 |
| 用 Matrix / Signal 协议库 | 安全性最高 | 要重写整个消息层，不推荐自研 |

## 8. 我的建议

- 如果你的朋友只有 2~3 个、聊天内容不算极端敏感 → **不做完整 E2EE**，改为：
  1. 消息 30 天自动清理（降低历史暴露）
  2. 加强邮箱/账号安全（2FA）
  3. App 启动加生物识别锁
- 如果确实要“连服务商都看不到” → 按 0.6 → 0.7 → 0.8 分三步做，先回第 6 节的 4 个问题。
